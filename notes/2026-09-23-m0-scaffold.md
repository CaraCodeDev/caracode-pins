## Core framing

Two things live in this repo, and they must not blur:

| Thing | What it is | Published? | Lives in |
|---|---|---|---|
| **The package** | `@caracode/pins`, an Astro integration that adds a dev-toolbar app | Yes, to npm (M4) | `packages/pins/` |
| **The playground** | A throwaway-looking but realistic Astro marketing page to test against | Never | `playground/` |

The playground is a **test fixture**, shaped to exercise the spec: its homepage
has the exact sections the spec uses as examples (notes/spec.md → "Purpose &
scope"), and a repeated component so later milestones can test notes/spec.md →
"Component by default". It should look like a plausible real site, not a lorem
ipsum grid, because pins get placed on real-looking elements.

## Decisions (locked 2026-09-23)

1. **Package lives at `packages/pins`, named `@caracode/pins`.** The `@caracode`
   npm scope is already Rich's (`@caracode/vivid-cli` is published there), and
   `@caracode/pins` is unclaimed as of 2026-09-23. The playground depends on it
   via `workspace:*`, exactly as a real site would depend on the published package.
2. **The package ships built JavaScript from day one**, not TypeScript source.
   It gets published in M4, and a real site loads it from `node_modules`, where
   nothing transpiles it. Building from the start means the playground exercises
   the same shape a real install will. Source is TypeScript; the build tool is
   the builder's choice. `pnpm dev` at the root must run the package's watch
   build and the playground's dev server together, so an edit to the package
   shows up in the playground without a manual rebuild.
3. **The playground runs on port 4358, and must fail rather than drift.** Another
   Astro project is usually running on 4321 (see `CLAUDE.md` → "Local dev").
   Astro's default behaviour when a port is busy is to quietly take the next one,
   which would put us on a surprise port or next to Rich's other project. **Set
   the port to 4358 and make a busy port an error.**
4. **Plain CSS in the playground, no Tailwind or UI framework.** It's a fixture;
   fewer dependencies means fewer things to break across Astro upgrades, and
   the markup stays close to what Astro renders, which matters for anchoring in M1.
5. **The integration only acts in dev.** Even in M0, when the only thing it does
   is add a toolbar app, it must not add anything to a production build
   (notes/spec.md → "Non-functional requirements", zero footprint). Checked in
   the verify below so it's true from the first commit.
6. **The toolbar app is identified as `caracode-pins`, shown as "Pins".** The
   panel for M0 is a heading and one line saying no pins yet. No design work in
   M0: the panel's look is established in M2.

## Watch-outs / known limitations

- **Port 4321 is Rich's other project.** Never stop or restart anything on 4321;
  never start the playground without the port pinned.
- **pnpm 12 may ask to approve build scripts** for dependencies like `esbuild` or
  `sharp`. That's interactive; hand it back to Rich (see verify step 1).
- **Workspace symlinks and the toolbar entrypoint.** The toolbar app's
  entrypoint is loaded by Vite in the browser. Resolving it from a symlinked
  workspace package can behave differently from a real `node_modules` install.
  If it only works via a path hack, flag it: M4 publishes this.
- **Astro 7 is recent.** Anything that differs from what the spec assumed about
  the toolbar (e.g. no room for a panel, no messaging to the dev server) is a
  stop-and-flag, not an improvisation. It changes the M1 plan.
